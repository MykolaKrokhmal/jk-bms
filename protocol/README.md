# Protocol catalog — how to run it

Architecture and evidence reasoning: `../docs/adr/0001-protocol-catalog.md` (see the third-pass
addendum for the claim-level evidence model and the single-pipeline architecture, and the
fourth-pass addendum for `owner_write_override` and which fields it currently covers).
Full audit of this stage's work: `../proj_arc/STAGE_1_COMPLETION_AUDIT.md`.

## Files

- `registers.canonical.json` — **hand-maintained.** Every BMS register this project reads or
  writes. Edit this directly for any register/field change. Its `evidence` arrays cite
  `protocol/evidence/sources.json` by `source_id` — see below, not a bare alias. A field's
  `effective_access` is normally derived automatically from its evidence (never hand-edited);
  the ONE exception is `owner_write_override: {authorized, authorized_by, date, rationale}` — a
  human-authored, fully attributed field that lets the repo owner explicitly accept the
  residual evidence gap for one specific field on their own hardware and re-enable its real
  write path, WITHOUT forging `verification_status` (which keeps reporting the true, unverified
  evidence status). `tools/protocol/lib/semantic-checks.js` enforces both directions: no field
  may reach `effective_access: "rw"` without either `verification_status: "confirmed"` or a
  well-formed override, and an override may never appear on a field the protocol doesn't itself
  declare `"rw"`. As of the fifth-pass addendum, all 46 protocol-RW fields carry one — see that
  addendum for the two distinct gates it bypasses (`verification_status` and, for 9 fields, an
  unresolved `dynamic_dependency`) and why `setup_passcode` gets its own dedicated UI rather than
  a generic register-list row.
- `non_register_entities.canonical.json` — **hand-maintained.** Calculated ESPHome / ESP32 /
  browser-UI / local-config entities that are NOT BMS registers.
- `schema/*.schema.json` — JSON Schema for the two files above.
- `evidence/sources.json` — **hand-maintained**, except for the one field below, which is
  updated only through the controlled tool that owns it. The evidence manifest: one entry
  per real source (official docs [unavailable], the workbook, the pinned upstream commit,
  this project's own implementation, the hardware audit), each with a content/revision
  `fingerprint`, `provenance_status`, and `derivation_group` — the sole determinants of
  whether two citations are actually independent of each other. Every citation elsewhere
  must carry the exact fingerprint recorded here; `tools/protocol/pipeline.js` refuses to
  run if `project_implementation.fingerprint` doesn't match a fresh hash of the real
  `batterylifepo4.yaml`+`jk_bms.js`. **Never hand-edit this fingerprint, and never treat a
  matching hash as proof the implementation is protocol-correct** — it only proves the
  citation's content is current; correctness is what `verification_status`/
  `owner_write_override` track. Re-stamp it only through
  `tools/protocol/fingerprint.js` (below).
- `evidence/build_workbook_index.py`, `build_upstream_index.py`, `build_implementation_index.py`
  — **generated outputs; the scripts themselves are hand-maintained.** Normalize the three raw
  sources into address-indexed JSON. Run individually only for debugging — normal use is
  through `tools/protocol/pipeline.js` (below).
- `evidence/build_claim_matrix.js` — reads the three indices + `sources.json` +
  `registers.canonical.json` and writes `generated/claim_matrix.json`, the full per-field
  claim-coverage matrix. Also run through the pipeline, not directly.
- `generated/*` — **generated, do not edit by hand.** Regenerate with the commands below.
  `generated/.fingerprint-review.json` is a transient workflow artifact from
  `tools/protocol/fingerprint.js review` (gitignored, not a build output).
- `fixtures/negative/*.json` — generated by the negative-fixture test (see below); also not
  hand-edited.

## Implementation fingerprint workflow (`tools/protocol/fingerprint.js`)

Hand-editing `project_implementation.fingerprint` (and its 239+ citations in
`registers.canonical.json`) is not a normal workflow step — it is exactly the failure mode
this tool exists to close. The single reusable hash implementation lives in
`tools/protocol/lib/fingerprint.js` (also `require()`'d by `tools/protocol/pipeline.js`, so
there is only ever one algorithm to drift out of sync with itself). Three modes, none of
which need the private workbook (only `pipeline.js build`/`check` ever do):

```bash
# Read-only: compute the actual fingerprint, compare to what's stored, change nothing.
node tools/protocol/fingerprint.js check

# Read-only: write a machine-readable drift report to
# protocol/generated/.fingerprint-review.json — captures the CURRENT exact state
# (content digests of batterylifepo4.yaml+jk_bms.js, registers.canonical.json,
# non_register_entities.canonical.json, and sources.json minus the fingerprint field
# itself, plus the exact count of the old fingerprint string in each citation file) so
# `accept` can later prove none of it moved since this review. Expires after 24h by
# default (--ttl-seconds to change).
node tools/protocol/fingerprint.js review

# Mutating, and the ONLY thing in this workflow that writes: re-verifies every one of
# review's captured conditions against the CURRENT state (source unchanged, canonical
# unchanged, sources.json unchanged outside the fingerprint field, review not expired,
# the old fingerprint's occurrence count in each citation file matches what review
# recorded), runs the full canonical validator (test/register_catalog/validate.js), and
# ONLY THEN rewrites protocol/registers.canonical.json's `source_fingerprint` citations and
# protocol/evidence/sources.json's `project_implementation.fingerprint` — atomically, with
# a post-write self-check and an automatic rollback if anything is inconsistent.
node tools/protocol/fingerprint.js accept
```

`accept` refuses (with a stable `reasonCode`, printed as JSON on stdout and as text on
stderr — never a raw stack trace) if: no review exists, the review has expired, the source
files changed since the review, `registers.canonical.json`/`non_register_entities.canonical.json`
changed since the review, `sources.json` changed (outside the fingerprint field) since the
review, canonical validation fails, or the live occurrence count of the old fingerprint
string doesn't match what the review recorded. It never touches
`protocol/generated/claim_matrix.json` (or any other generated artifact) — those are the
pipeline's job (`tools/protocol/pipeline.js build`) once the citation files are current.
See `protocol/evidence/IMPLEMENTATION_DRIFT_REVIEW.md` for the itemized review of every
change that actually caused fingerprint drift in this repo's history, and why each one was
restamp-admissible.

## Single pipeline (normal way to rebuild everything)

```bash
# Rebuild every index, the claim matrix, and every generate.js output, from a hash-verified
# workbook — never writes anything until every step has succeeded (isolated staging dir):
node tools/protocol/pipeline.js build --workbook /path/to/LiFePO4_BMS_Parameters_registers.xlsx
#   (or: JK_BMS_WORKBOOK_PATH=/path/to/file.xlsx node tools/protocol/pipeline.js build)

# CI-safe: verify every derived artifact is byte-identical to what `build` would produce,
# without writing anything (also checks the Node version pin and that the external
# component isn't pinned to a mutable @main/@master/@latest ref):
node tools/protocol/pipeline.js check --workbook /path/to/LiFePO4_BMS_Parameters_registers.xlsx
```

`build` takes an exclusive lock (`protocol/generated/.pipeline.lock`) — a second concurrent
`build` is rejected outright (`PIPELINE_LOCKED`), never silently interleaved.

If you only edited `registers.canonical.json`/`non_register_entities.canonical.json` by hand
and did NOT touch `batterylifepo4.yaml`/`jk_bms.js`, `tools/protocol/generate.js` alone
(below) is enough — the full pipeline additionally re-derives the workbook/upstream/
implementation indices and the claim matrix, which only changes if the underlying evidence
sources changed.

## After editing a canonical source file (generate.js alone)

```bash
# 1. Regenerate register_catalog.json, the coverage report, and jk_bms.js's generated block:
node tools/protocol/generate.js

# 2. Run the full validator (schema + semantic invariants incl. claim-coverage/fingerprint/
#    independence checks + drift-check + cross-file YAML/JS/mock checks + UI-order +
#    unit-glossary + regression tests):
node test/register_catalog/validate.js

# 3. Packed-register codec round-trip tests:
node test/protocol_catalog/test_packed_codec.js

# 4. Negative-fixture tests (54 mutation classes; proves the validator's failure paths fire):
node test/protocol_catalog/test_negative_fixtures.js
#    Pass --write-fixtures to also (re)write protocol/fixtures/negative/*.json.

# 5. Everything above, plus the C++/topology suites and (if JK_BMS_WORKBOOK_PATH is set)
#    the single-pipeline check, in one command:
bash test/run_all.sh
```

## CI-safe drift check (no writes)

```bash
node tools/protocol/generate.js --check
```

Exits non-zero if `register_catalog.json`, `protocol/generated/coverage_report.md`,
`protocol/generated/.generation-manifest.json`, or jk_bms.js's generated block is stale
relative to the two canonical source files. This does NOT catch a stale
`workbook_index.json`/`upstream_index.json`/`implementation_index.json`/`claim_matrix.json` —
use `tools/protocol/pipeline.js check` for that.

Note: `generate.js` no longer produces a C++ header or a standalone frontend projection — both
existed only to be described in a report, were never consumed by any real build target or
frontend code, and were removed as misleading non-runtime outputs.

## Verifying against the real firmware build

```bash
esphome config batterylifepo4.yaml     # config validity only
esphome compile batterylifepo4.yaml    # full compile — see the audit for RAM/Flash deltas
```

Neither of these performs a hardware write. This project does not flash or write to a real
device from this tooling — see `docs/adr/0001-protocol-catalog.md` and the governing
`IMPLEMENTATION_ROADMAP.md` for why.
